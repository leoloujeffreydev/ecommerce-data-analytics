LJ DEV COMMERCE — STANDARD ETL WORKFLOW
RAW DATA → CLEAN CSV → DATABASE-READY → POSTGRESQL

CORE RULE

WORKFLOW STRUCTURE = STANDARDIZED

DATA FINDINGS / TRANSFORMATIONS / VALIDATION RULES = DATASET-SPECIFIC


============================================================
01. EXTRACT & ANALYZE
============================================================

1.1 Setup
- Import required libraries
- Configure display/options if needed
- Define project paths
- Load required reusable tools, such as the data profiler

1.2 Load Raw Dataset
- Define the raw dataset path
- Load the source CSV/file
- Create the standardized raw DataFrame:

<dataset_name>_raw

1.3 Initial Inspection
Review the untouched raw dataset:
- Shape
- Column names
- Data types
- Sample records
- Basic null information

No data modification.

1.4 Run Profiler
Run the reusable profiler against the untouched raw DataFrame.

The profiler may identify:
- Missing values
- Duplicates
- Whitespace
- Potential datatype issues
- Date issues
- Numeric issues
- Categorical patterns
- Identifier patterns
- Other detected data-quality issues

Profiler results are findings, not automatic transformation instructions.

1.5 Review Profiling Results
Review the complete profiler output.

This separates:
- Automated profiling findings
- Issues requiring analyst review
- Potential business-rule decisions
- Potential transformation candidates

No data modification.

1.6 Review Profiler Issues
Review the specific ISSUES output separately.

For every detected issue, determine whether it is:
- Real issue
- False positive
- Expected business value
- Requires transformation
- Requires further investigation

1.7 Independent Analyst Review
Perform dataset-specific checks beyond the automated profiler.

Examples may include:
- Primary/business key uniqueness
- Duplicate investigation
- Category/value consistency
- Business-rule validation
- Cross-column validation
- Date logic
- Referential relationships
- Raw datatype suitability
- Source-system conventions

IMPORTANT:
This section must include datatype preparation requirements even if the profiler successfully recognizes a semantic datatype.

Example:

Profiler detects CreatedOn as DATE

But pandas raw dtype = object

Therefore:
Transformation required later:
object → datetime

1.8 Transformation Decisions
Document the final approved decisions.

For every potential transformation:

Column
Current State
Issue / Requirement
Decision
Transformation
Reason

Only transformations approved here proceed to Section 2.


============================================================
02. TRANSFORM
============================================================

2.1 Create Clean DataFrame
Create a separate working copy:

<dataset_name>_clean = <dataset_name>_raw.copy()

RULE:

RAW DATAFRAME = NEVER MODIFIED
CLEAN DATAFRAME = TRANSFORMATION WORKING COPY

2.2 Apply Approved Transformations
Apply only transformations approved in Section 1.8.

Possible examples:
- Trim whitespace
- Convert datatype
- Standardize values
- Handle approved missing values
- Remove approved duplicates
- Correct documented formatting issues

The transformations themselves are dataset-specific.


============================================================
03. VALIDATE
============================================================

3.1 Transformation Validation
Validate every transformation performed.

Validation must correspond directly to the transformation.

Examples:

Whitespace removed:
→ Confirm no unintended leading/trailing whitespace remains

Date conversion:
→ Confirm datetime datatype
→ Confirm invalid dates were handled according to the approved decision

Category standardization:
→ Confirm expected final category values

Duplicate removal:
→ Confirm approved duplicate logic worked

3.2 Data Preservation Validation
Confirm that transformations did not unintentionally damage unrelated data.

Depending on the dataset:
- Row count preservation, when expected
- Column preservation
- Unaffected column preservation
- Key preservation
- Expected records retained
- No unexpected data loss


============================================================
04. CLEAN CSV
============================================================

4.1 Export Clean Dataset
Export the validated Clean DataFrame to the standardized Clean folder.

Example:

data
└── <dataset_folder>
    └── clean
        └── <dataset_name>_clean.csv

4.2 Verify Exported Clean CSV
This is a required pipeline stage.

Read the exported CSV back:

<dataset_name>_clean_csv

Verify:
- File successfully loads
- Row count matches
- Column structure matches
- Data values are preserved
- Required datatypes are restored/parsed correctly when reading

PIPELINE HANDOFF:

CLEAN DATAFRAME
      ↓
EXPORT
      ↓
CLEAN CSV FILE
      ↓
READ BACK
      ↓
VERIFIED CLEAN CSV DATAFRAME

The Clean CSV is therefore not just a backup.

It is the official handoff artifact between:

DATA CLEANING
        ↓
DATABASE PREPARATION


============================================================
05. DATABASE READY
============================================================

5.1 Define Source → Target Mapping

Before creating the database-ready DataFrame, explicitly define and review:

VERIFIED CLEAN CSV COLUMN
            ↓
POSTGRESQL TARGET COLUMN
            ↓
TARGET DATATYPE
            ↓
DATABASE RULE / CONSTRAINT

The mapping must be based on the project's actual database design/documentation.

Review:
- Source column name
- Target SQL column name
- Target datatype
- Nullable / required status
- Primary key role
- Foreign key role
- Default values, if applicable
- Any required transformation specifically for database compatibility

IMPORTANT:

Do not guess SQL structure.

Use the project's source of truth for:
- Source-to-target mapping
- Database schema/design
- Relationship map
- Load order
- Existing table structure

5.2 Create Database-Ready Dataset FROM EXPORTED CSV

Create:

<dataset_name>_db_ready

Starting from:

<dataset_name>_clean_csv

—not directly from the in-memory Clean DataFrame.

PIPELINE:

VERIFIED CLEAN CSV
        ↓
SOURCE → TARGET MAPPING
        ↓
COLUMN RENAMING / REORDERING
DATATYPE PREPARATION
DATABASE-SPECIFIC REQUIREMENTS
        ↓
DATABASE-READY DATAFRAME

5.3 Database-Ready Validation

Validate the database-ready DataFrame before PostgreSQL loading.

Check as applicable:
- Row count
- Expected target columns
- Column order
- Target-compatible datatypes
- Required fields
- Nullability
- Primary key uniqueness
- Foreign key readiness
- Mapping completeness
- No undocumented source columns lost


============================================================
06. POSTGRESQL
============================================================

6.1 Connect
Connect to PostgreSQL.

Confirm:
- Connection successful
- Correct database
- Correct schema

6.2 Prepare / Create Target Table

Before creating anything:
- Check whether the table already exists
- Review the approved target design
- Confirm schema name
- Confirm table name
- Confirm PostgreSQL datatypes
- Confirm constraints

Then:

CREATE TABLE

only if required by the project workflow.

We should not blindly recreate existing tables.

6.3 Verify Table Structure

Verify the actual PostgreSQL table:
- Column names
- Column order
- Data types
- NULL / NOT NULL rules
- Defaults

Compare it against the approved Source → Target Mapping.

6.4 Verify Keys, Relationships & Load Dependencies

Verify as applicable:
- Primary key
- Unique constraints
- Foreign keys
- Referenced parent tables

Also confirm load dependency:

Is the required parent/master data already loaded?

This must follow the project's ETL load order.

6.5 Insert Records

Load:

<dataset_name>_db_ready

into the verified PostgreSQL target table.

Use the approved loading method.

Avoid accidental duplicate loads.

6.6 Validate Row Count

Compare:

DB-READY SOURCE ROW COUNT
            vs
POSTGRESQL TABLE ROW COUNT

Account for the intended load scope.

6.7 Retrieve Records

Retrieve records from PostgreSQL to confirm the data is actually stored correctly.

Review:
- Sample records
- Column values
- Dates
- Boolean/numeric values
- Expected formatting

6.8 Source → Database Reconciliation

Compare:

DATABASE-READY DATASET
            ↓
POSTGRESQL TABLE

Validate:
- Row counts
- Key values
- Column values
- Record-level consistency where appropriate

This is different from merely checking that records exist.

6.9 Database Integrity Validation

Perform final dataset-specific database checks.

Examples:
- Primary key uniqueness
- Foreign key integrity
- Required fields
- Duplicate records
- Unexpected NULLs
- Business-rule checks
- Relationship integrity

6.10 Close Connection

Close PostgreSQL resources cleanly.

Confirm the database connection is closed.

6.2 Prepare / Create Target Table

First, check whether the target table exists in PostgreSQL.

If the target table already exists:
Do not recreate the table.
Proceed to the next table structure/validation step.
If the target table does not exist:

Create the subsection:

6.2.1 Create Target Table

This subsection must:

Follow the same structure and coding pattern as the Warehouse notebook.
Create the table using the approved Data Dictionary.
Define the Primary Key.
Apply NOT NULL only to fields marked Required.
Allow NULL for fields marked Optional.
Use PostgreSQL-compatible data types based on the Data Dictionary.
Add Foreign Keys only when defined in the approved Database Design.
Use try / except, conn.commit(), and conn.rollback() following the established Warehouse pattern.
Confirm successful table creation.

After successful creation, continue with the table structure verification step.
