STEP 2 — SALES ORDER TRANSFORMATION DECISION REVIEW

We have 10 decisions/items to review.

Decision 1 — SourceOrderIDInternal → sales_order_id

Finding: Both order identifiers are unique, but SourceOrderIDInternal follows the target ID pattern:

SHOPIFY-SO001 → SO001
AMAZON-SO008 → SO008
NOON-SO015   → SO015

The Data Dictionary example is SO001.

Recommendation

APPROVE

SourceOrderIDInternal
        ↓
sales_order_id

SourceOrderID remains source-level traceability information but will not be added as an undocumented target column.

Decision status: 🟢 APPROVE

Decision 3 — CampaignCode → campaign_id

Campaign is explicitly optional in the approved Data Dictionary.

Decision 9 — CAM002 / SO005 anomaly

This is the only major business-rule exception.

We have:

SO005
OrderDate = 2026-07-09
CampaignCode = CAM002

while CAM002 begins:

2026-07-15

Therefore:

Order:    July 9
Campaign: July 15 → August 31

        ⚠️ BEFORE CAMPAIGN START

The project documentation explicitly says this should not be automatically corrected.

Recommendation

APPROVE RETENTION

Keep:

campaign_id = CAM002

Do not:

remove CAM002
change the order date
change the campaign dates
delete SO005
assign another campaign

Instead, document it as a business-rule exception.

Decision status: 🟢 APPROVE — RETAIN & FLAG

Decision 10 — Shipping/Billing addresses

All 20 records currently have:

ShipToAddress = BillToAddress

This is unusual but not proven incorrect.

The target explicitly has separate:

shipping_address
billing_address

fields.

Recommendation

APPROVE — NO CORRECTION

Map independently:

ShipToAddress → shipping_address
BillToAddress → billing_address

Even when the values happen to be identical.

Decision status: 🟢 APPROVE
