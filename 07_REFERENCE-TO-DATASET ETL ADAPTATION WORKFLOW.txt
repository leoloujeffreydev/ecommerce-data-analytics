========================================================
DO NOT CONFUSE DUPLICATES
========================================================

A repeated identifier does NOT automatically mean duplicate records.

Always distinguish between:

- exact duplicate rows
- duplicate primary-key candidates
- repeated parent foreign keys
- repeated product/customer identifiers
- legitimate one-to-many relationships
- cross-source identifier collisions
- composite-key uniqueness

Example:

A Sales Order ID appearing on multiple Sales Order Item rows is expected.

Do NOT deduplicate those rows.

Similarly, a ProductCode appearing on multiple transaction rows may be legitimate.

========================================================
TRANSFORMATION CONTROL
========================================================

Never transform data merely because a transformation is technically possible.

Every transformation must have an approved reason.

Use the decisions established in Section 1.8.

Approved classification categories:

- Safe deterministic transformation
- Valid value — retain unchanged
- Expected business behavior
- Requires relationship validation later
- Requires business investigation

Section 2.2 must apply ONLY approved transformations.

Do NOT silently:

- remove outliers
- fill NULLs
- drop rows
- deduplicate
- recalculate business values
- overwrite source values
- standardize categories
- trim fields
- change identifiers

unless that action was explicitly approved.

========================================================
SOURCE DATA PRESERVATION
========================================================

Raw datasets must remain unchanged.

Use separate clean/working DataFrames.

For multiple source datasets:

- inspect separately
- profile separately
- review separately
- make source-specific decisions where necessary
- transform separately
- validate separately

Only after source-specific validation is complete should controlled consolidation occur.

Consolidation is NOT reconciliation.

Maintain source lineage throughout the process.

========================================================
VALIDATION PRINCIPLE
========================================================

Every approved transformation needs a corresponding validation.

If Section 1.8 approves:

CreatedOn → datetime

then Section 3.1 must verify CreatedOn is datetime.

If Section 1.8 approves:

UnitPrice → Decimal

then Section 3.1 must verify UnitPrice is Decimal-compatible.

If Section 1.8 says:

retain outlier unchanged

then validation should confirm that the value was not removed or altered.

Validation must correspond to approved decisions.

Do not create unrelated validation requirements.

========================================================
RELATIONSHIP VALIDATION
========================================================

Relationships must be validated against the actual completed target/master tables.

Do not assume relationship readiness just because identifiers look correct.

Examples:

Sales Order Item → Sales Order
Sales Order Item → Product
Sales Order → Customer
Sales Order → Marketing Campaign

The exact relationships depend on the new dataset's Data Dictionary and database design.

========================================================
DATATYPE TRANSFORMATION RULE
========================================================

Every typed target field must be reviewed.

Pay particular attention to:

- dates → datetime
- monetary values → Decimal
- integer quantities → integer
- identifiers → text
- optional foreign keys → nullable compatible values

Do not change business meaning merely to satisfy a datatype.

Datatype conversion is a technical transformation unless it changes the actual business value.
